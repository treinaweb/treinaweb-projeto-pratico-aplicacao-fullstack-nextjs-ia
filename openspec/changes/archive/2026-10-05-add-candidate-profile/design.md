# Design

## Context

Builds on `add-user-auth`: `requireSession()` (`lib/auth/session.ts`) already gates a route to a signed-in candidate, and `define-platform-architecture/design.md` already decided PostgreSQL + Prisma behind `lib/db/repositories` (one file per entity), one Zod schema per entity, and `app/` only orchestrating. This is the first capability to add application-owned Prisma models alongside the ones Better-Auth's CLI generates and owns (`User`, `Session`, `Account`, `Verification`).

See `proposal.md` for motivation; see `specs/candidate-profile/spec.md` for the nine requirements this design implements (personal info + seven list entities + ownership).

## Goals / Non-Goals

**Goals:**
- Model personal info and seven list entities (work experience, education, courses, projects, links, skills, languages) as Prisma models owned entirely by this capability.
- Enforce per-candidate ownership at the data-access layer, not just in the UI.
- Keep the new models and migrations isolated from Better-Auth's generated schema so a future `npx auth generate` re-run can't touch them.

**Non-Goals:**
- Feeding this data into resume generation, job matching, or any AI feature — those are separate capabilities that will consume this data later.
- File uploads (e.g. a profile photo or attached certificates) — not requested, and out of scope for this change.
- A generic/dynamic form-builder abstraction over the seven list entities — each gets its own small, concrete component instead (see Decision 4).

## Decisions

**1. `CandidateProfile` is the single link to `User`; nothing else references `User` or Better-Auth's schema.**
`CandidateProfile.userId` is a plain `String` column holding `User.id` by convention, with **no** Prisma `@relation` to the `User` model (no back-relation field is added to `User` either). All seven list entities (`WorkExperience`, `Education`, `Course`, `Project`, `ProfileLink`, `Skill`, `Language`) relate to `CandidateProfile` via `profileId`, never directly to `User`.
*Why*: Better-Auth's CLI (`npx auth generate`) regenerates its own models into the same `prisma/schema.prisma` file and reported "Schema was overwritten" the one time it ran so far (see `add-user-auth/design.md`'s risk notes). Keeping every application model's only touchpoint with `User` a plain, relation-free `userId` string means a future Better-Auth regeneration has nothing to invalidate — our models don't depend on `User`'s shape or Prisma's relation metadata for it. A `CandidateProfile` row is looked up with a plain `findFirst({ where: { userId } })`, not a Prisma relation traversal.
*Alternatives considered*: a Prisma `@relation` from `CandidateProfile` to `User` with a back-relation field (rejected — couples an application model to a vendor-generated one that gets regenerated by an external tool outside our migration control).

**2. `CandidateProfile` is created lazily on first visit to `/profile`.**
There is no separate "set up your profile" step; `getOrCreateProfile(userId)` in `lib/db/repositories/candidate-profile.ts` creates an empty profile row the first time a candidate's `userId` has none.
*Why*: every candidate ends up needing a profile, and a distinct creation step would just add friction without protecting anything.
*Alternatives considered*: creating the profile row at registration time in `add-user-auth`'s sign-up flow (rejected — would couple an unrelated capability's Server Action to this one; lazy creation keeps the dependency one-directional).

**3. Ownership is enforced in `lib/db/repositories`, not just by rendering the page behind `requireSession()`.**
Every repository function for a list entity takes the authenticated `userId` alongside the entity id, and scopes the query through the owning profile — e.g. an update targets `WHERE id = :entityId AND profile.userId = :userId` — rather than trusting a client-supplied id alone. A mismatched id (not found, or owned by someone else) returns "not found," never a distinct "forbidden," so existence of another candidate's row is never revealed. Every Server Action also calls `requireSession()` itself, per Next.js's own guidance to verify authorization inside each Server Action rather than relying on the page alone.
*Why*: this is what the spec's "Profile data ownership" requirement actually demands, and doing it at the repository layer means every call site gets it for free instead of each of ~20 Server Actions re-implementing the check.
*Alternatives considered*: checking ownership only in the Server Action before calling a generic repository update (rejected — easy to forget on one of the ~20 actions; scoping the query itself makes the mistake structurally harder to make).

**4. Each of the seven list entities gets its own small section component; no generic form-builder.**
`components/profile/<entity>-section.tsx` (e.g. `work-experience-section.tsx`) renders that entity's list plus its own add/edit form, each backed by its own Zod schema in `lib/validation/profile.ts` and its own Server Actions in `app/profile/actions.ts`.
*Why*: the seven entities share a CRUD *shape* but have different fields; a generic component parameterized enough to cover all of them would be more complex than seven concrete ones, for no real reuse benefit at this scale.
*Alternatives considered*: one generic `<ProfileListSection fields={...} />` component (rejected — the field-schema abstraction needed to cover dates, optional URLs, and enums ends up as complicated as the thing it replaces).

**5. Forms use Server Actions with `useActionState`, not the client-SDK pattern from `add-user-auth`.**
Each form is a `"use client"` component calling `useActionState` against a Server Action that re-validates with the matching Zod schema server-side and returns field errors; there's no separate client-only validation pass before submission.
*Why*: `add-user-auth`'s forms called Better-Auth's own client SDK, which is itself the secure server boundary — there was no separate data layer to protect. Here, Server Actions *are* that boundary (per Next.js's own forms guidance), so validating only server-side and surfacing errors via `useActionState` is the direct, idiomatic path, without duplicating the Zod call on the client for no added safety.
*Alternatives considered*: mirroring the auth forms' client-side-Zod-then-call pattern (rejected — there's no vendor client SDK here to call; it would just be an extra validation pass with no new boundary behind it).

**6. One `/profile` page, not one route per entity.**
`app/profile/page.tsx` is a single Server Component rendering the personal info form and all seven section components. There is no `/profile/experience`, `/profile/education`, etc.
*Why*: keeps this MVP boilerplate simple; a candidate managing their profile benefits from seeing everything in one place, and splitting into sub-routes adds navigation complexity nothing here calls for.
*Alternatives considered*: a route per entity (rejected — more routing and layout work for no behavior this spec requires; revisit if the single page becomes unwieldy).

**7. The dashboard gets a link to `/profile`.**
`app/dashboard/page.tsx` (currently boilerplate) adds a link to `/profile`.
*Why*: `/profile` would otherwise be unreachable from the UI, the same gap `add-user-auth` closed for the landing page's `/register` and `/login` links.

## Risks / Trade-offs

- [Risk] `prisma/schema.prisma` is a single shared file; even with Decision 1's isolation, a future `npx auth generate` re-run could in principle overwrite the whole file, not just `User`/`Session`/`Account`/`Verification` → Mitigation: this is a process risk, not something code can prevent. Document (here, and reiterated in the apply task for whoever regenerates it next) that any future `auth generate` re-run must be diffed against git before committing, to confirm the application's own models (`CandidateProfile` and friends) survived.
- [Risk] Lazy profile creation means a first-time `/profile` visit does a write (`getOrCreateProfile`) before rendering → Mitigation: a single cheap upsert-style check; acceptable for MVP traffic.
- [Trade-off] No Prisma relation from `CandidateProfile` to `User` means no DB-level cascade delete if a `User` row is ever removed; an orphaned `CandidateProfile` would need an explicit cleanup query → accepted, since account deletion isn't implemented yet in any capability; revisit when it is.

## Migration Plan

Additive only — new Prisma models and one migration, no existing table touched. Build order: Prisma models (`CandidateProfile` + seven list entities) and migration first, then repositories, then validation schemas, then Server Actions, then the `/profile` page and its section components, then the dashboard link.
